# CLAUDE.md

Working rules for Claude sessions in this repository. Read this first; it replaces re-reading old conversations.

## Communication

- Work and reply in English. Address the owner as Mic. Keep replies short and direct: what was done, what was verified, what Mic needs to decide.
- State results faithfully: if a check failed or a step could not be run, say so with the output.

## Product principle (do not break)

- The LLM only reads the design doc and maps doc names to code IDs. Code facts (components, imports) and every drift conclusion come from deterministic Go code.
- Only the doc text and component/import IDs go to the API, never source code, file paths or import sites.
- Go stdlib (`go/parser`) only. The single external dependency is `github.com/anthropics/anthropic-sdk-go`. No YAML library: config is JSON.
- Default model: `claude-sonnet-5-5`.
- `docs/architecture-rules.md` (ADR-001) encodes these rules for the code; `scripts/check.sh` enforces them on every run (dogfood).

## Where things are

- Release plan (one release every Thursday, to v1.0.0 on Dec 31): `docs/release-plan.md`, with the weekly release gate.
- Roadmap and the next task: `docs/ROADMAP.md`. "Do the next step" means the first item with status `next`, or the first `todo` if none is `next`.
- User docs: `README.md` (index) and `docs/guide/` (usage, configuration, ci, how-it-works, development).
- Release notes: `CHANGELOG.md` (an `## Unreleased` section collects changes until the next tag).
- Pilot material and offline evaluation: `pilot/`, `pilot/eval/` (replays recorded locks, no API call).

## Workflow

1. Start from the latest `origin/main` on a new branch named for the change: `feat/<thing>`, `fix/<thing>`, `docs/<thing>`. Never reuse a merged branch. Do not push to `main`.
2. Make the change with tests. Update `docs/guide/` and `CHANGELOG.md` (`## Unreleased`) when behaviour or usage changes.
3. Run `scripts/check.sh` before every push (gofmt, vet, tests, fixture runs, dogfood). Do not push on failure. Gate the commit on the script's own exit code (`scripts/check.sh && git commit ...`); piping it into `tail` or `grep` hides a failure.
4. Commit messages: a short subject, a body with why and what was verified. **No attribution or co-author lines.**
5. Push with `git push -u origin <branch>`. Open a pull request **only when Mic asks** (or use the `/ship` skill when asked to ship).
6. PR body sections: Problem, Change, Verification, and "After merging" when Mic must act. The PR body must not end with a "Generated by" footer: the server adds one on create, so update the PR body right after creating it.
7. After opening a PR, subscribe to its activity and fix CI failures on that branch. Never merge; Mic merges.
8. After Mic merges, check CI on `main` before starting the next item.

## Limits of the cloud session

- Only `stmic168/arch-drift` is reachable. Do not run archdrift on other repositories except through the `pilot` workflow, with Mic's approval.
- Pushing tags and deleting branches are blocked by the git proxy. Do not work around it; tell Mic the UI steps (releases: see `docs/guide/development.md`).
- There is no `ANTHROPIC_API_KEY` in the session. Live API runs go through the `pilot` or `live-check` workflows (they cost tokens; ask first unless Mic asked for the run).

## Skills

- `/ship`: check, commit, push, open the PR and clean its body.
- `/next`: check CI on `main`, pick the next roadmap item, do it, update the roadmap.
- `/pilot`: run the pilot workflow on a public repository and score it with the offline eval.
